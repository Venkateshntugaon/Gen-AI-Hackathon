## Phase 1: Data models and sample data  (2026-11-25)
**What we built:** Pydantic models for a question (MCQ), a finding, a suggestion and a review result. A script that saves 100 random SciQ questions (seed 42, no support passage) to a CSV, and a script that writes a 10-question teacher-style question paper (DOCX) with 3 deliberately flawed questions.
**Why:** SciQ gives real, verified science MCQs. The sample paper mimics what teachers actually upload, and the planted flaws (Q2 duplicate option, Q4 implausible option, Q7 also-correct option) let the demo show findings. MCQ is frozen, so code cannot change the verified answer in place.
**Files:** src/reviewer/models.py, scripts/make_sciq_sample.py, scripts/make_sample_docx.py, data/sample/sciq_sample.csv, data/sample/sample_paper.docx
**How to verify:** `python scripts/make_sciq_sample.py` → "Saved 100 questions …"; `python scripts/make_sample_docx.py` → "Saved 10 questions (3 with planted flaws) …"; `python -c "from src.reviewer.models import MCQ"` runs without error.
**Notes / issues:** Each CSV id keeps the original SciQ train-row number (e.g. "SciQ #8279"), so every question can be traced back to the dataset. Option text in the paper is capitalised for realism; the question text is copied as-is, including SciQ's own typos.

## Phase 2: Document ingestion (PDF, DOCX, TXT, CSV)  (2026-11-25)
**What we built:** Readers that turn PDF (pdfplumber, with page markers), DOCX (paragraphs and table cells, in document order), TXT and SciQ-style CSV into text or MCQs. A regex parser that understands the common numbering, option and answer formats, including an answer-key block at the end of the paper. A Gemini fallback extractor used when the PDF is scanned (PDF bytes sent directly) or the parser result looks unreliable (0 questions, or more than 30% with fewer than 3 options).
**Why:** Teachers upload papers as they already have them. The regex is free, fast and predictable; Gemini only handles messy or scanned layouts. Answers are never guessed: a question without a marked answer gets `None` and the teacher picks it in the UI.
**Files:** src/reviewer/ingest/readers.py, src/reviewer/ingest/parser.py, src/reviewer/ingest/llm_extract.py, prompts/extract.md, tests/test_parser.py
**How to verify:** `pytest tests/test_parser.py` → 35 passed. `python -c "from pathlib import Path; from src.reviewer.ingest.llm_extract import extract_questions; q,llm=extract_questions('sample_paper.docx', Path('data/sample/sample_paper.docx').read_bytes()); print(len(q), all(x.answer for x in q), llm)"` → `10 True False`.
**Notes / issues:** `extract_questions()` (the read → parse → maybe-fallback decision) lives in llm_extract.py, because putting it in parser.py would create a circular import. The Gemini extractor calls the SDK directly; caching and retry come with llm.py in Phase 4. Extraction uses temperature 0 because it must copy text, not be creative.

## Phase 3: Detection (pipeline steps 2–4)  (2026-11-25)
**What we built:** Rule checks (duplicates, distractor equal to the answer, length and a/an answer cues, "all/none of the above"); an embedding similarity scan with all-MiniLM-L6-v2 on CPU (too close to the answer, too far from it, near-duplicate distractors); and an LLM judge that makes one Gemini call per question (temperature 0.2, JSON schema output) and maps the verdict to findings using the severity table. A merge step keeps one finding per (target, issue type) with the highest severity, all detecting layers, and the LLM's reason. We also built `llm.py` (prompt filling, JSON-schema call, disk cache, 2/4/8 s retry), because the judge is the first step that needs it.
**Why:** Cheap checks first, then embeddings, then the LLM, the most expensive and most capable. Each finding records which layer caught it, so the result is explainable.
**Files:** src/reviewer/llm.py, src/reviewer/pipeline/rules.py, src/reviewer/pipeline/similarity.py, src/reviewer/pipeline/judge.py, prompts/judge.md, tests/test_rules.py
**How to verify:** `pytest tests/test_rules.py` → 11 passed (`pytest -q` → 46 passed). Detection on the 10 sample-paper questions flags all 3 planted flaws: Q2 duplicate (rules + similarity + LLM), Q4 "A bicycle" implausible (similarity + LLM), Q7 "Steam" also_correct HIGH (LLM).
**Notes / issues:** `llm.py` is listed under Phase 4 in the plan, but was built now so the judge would not need rewriting later. The judge prompt's plausibility scale was made more explicit after the first run over-flagged reasonable distractors (see CHALLENGES.md). For duplicate / answer_cue verdicts (no row in the severity table) the LLM finding uses the same severity as the rule layer (low / medium).

## Phase 4: Improvement and guard (pipeline steps 5–7)  (2026-11-25)
**What we built:** A generator that makes one Gemini call per question to get 3 misconception-based candidates for every weak distractor. A validator that rejects candidates equal or too similar to the answer, duplicates of existing options, candidates with a length cue (outside 0.4×–2.5× the answer's length) and "all/none of the above", then makes one batched Gemini verify call per question. If no candidate survives, generation is retried once, with the rejected candidates listed in the prompt; if there is still nothing safe, the finding says "No safe replacement found." An answer lock fingerprints the answer (SHA-256) at load time and discards any result whose answer differs by even one character. A runner chains steps 2–7 with a progress callback.
**Why:** Generation without validation is unsafe, because an LLM can produce a second correct answer. The frozen MCQ, the validator and the fingerprint check are three independent layers that guarantee the hard rule.
**Files:** src/reviewer/pipeline/generator.py, validator.py, answer_lock.py, runner.py, src/reviewer/llm.py (retry update), prompts/generate.md, prompts/verify.md, tests/test_validator.py, tests/test_answer_lock.py
**How to verify:** `pytest tests/test_validator.py tests/test_answer_lock.py` → 18 passed (`pytest -q` → 60 passed). A full pipeline run on the 10 sample-paper questions takes ~2.5 min with free-tier waits: 10/10 answers preserved, and every flawed distractor gets a suggestion (Q2 "Protein" → "Tissues", Q4 "A bicycle" → "Petal", Q7 "Steam" → "Hot water").
**Notes / issues:** Generation uses temperature 0.7 (for variety) and verify uses 0 (strict). Duplicates are low severity but are also sent for replacement, because two identical options are a real flaw. The retry now waits as long as Gemini suggests for per-minute limits, and stops at once with a clear message when the daily limit is reached. `.env` was switched to gemini-3.5-flash-lite after the daily quota of gemini-3.5-flash ran out (see CHALLENGES.md).

## Phase 5: User interface  (2026-11-25)
**What we built:** A one-page Streamlit app with a header stepper (Upload → Confirm → Review → Results) in Alliance University colours. Upload accepts PDF/DOCX/TXT (CSV under "Advanced") and has a "Try a sample paper" button. Confirm shows an editable table with an A–D answer dropdown; "Start review" stays disabled until every question has an answer. Review shows a progress bar and a live findings count, keeps finished questions, and offers Retry when Gemini is busy. Results show summary metrics (including "Answers preserved n/n"), filters, and a card per question: options with severity badges, the locked answer, findings with "detected by" chips, a wrong-answer-key banner, and suggestions with Accept/Reject.
**Why:** Teachers are the users, so the flow must need no technical knowledge. The confirm step makes the "verified" answer really verified by a human, and accept/reject keeps the teacher in control.
**Files:** app.py, ui/components.py, ui/styles.css, .streamlit/config.toml, docs/screenshots/
**How to verify:** `streamlit run app.py` → "Try a sample paper" → "Start review" → results. Automated check with Streamlit's AppTest: the full flow reaches Results with no exceptions, metrics show 10 reviewed and 10/10 preserved, and Accept changes a suggestion's status.
**Notes / issues:** All question text is HTML-escaped before it is shown. Session state survives Streamlit reruns (button clicks, filters); a full browser reload starts a new session (see PENDING.md). The similarity model is loaded once with `st.cache_resource`.

## Phase 6: Export  (2026-11-25)
**What we built:** Three downloads on the Results page: the revised question paper (.docx) with accepted suggestions applied and an answer key at the end, a review report (.csv) with one row per finding (question id, target, issue type, severity, reason, detected by, suggestion, status, answer preserved), and the full results (.json) as a dump of all ReviewResult objects.
**Why:** Teachers work in Word, the CSV is for analysis, and the JSON is our evidence for evaluation and the report.
**Files:** src/reviewer/export.py
**How to verify:** On the Results page, accept a suggestion and download all three files. In the sample run, the revised DOCX showed "D) Fungus" (accepted) in Q1, and its answer key letters matched the original paper's answers exactly (checked by script).
**Notes / issues:** Only suggestions with status "accepted" change the paper. The answer is inserted back into its original position, so answer letters never move.

## Phase 5–6 follow-up: teacher-friendly downloads and UI polish  (2026-11-25)
**What we built:** After the team tried the app, two changes. (1) Teachers do not use CSV or JSON files, so the two main downloads are now Word documents: the revised question paper and a new **Review Report** (.docx) with a summary table, a "how to read this report" note, and every question with its options (correct answer marked "unchanged"), colour-coded findings in plain English, and suggested replacements with their accept/reject status. **Why:** The users are teachers, who work in Word. A PDF can be made from either document in Word (File → Save as PDF) without adding a PDF library.
**Files:** src/reviewer/export.py, app.py, ui/components.py, ui/styles.css
**How to verify:** `streamlit run app.py` → sample paper → Start review → "Accept all undecided" → download "Revised question paper" and "Review report", and open both in Word. AppTest run: full flow, Accept-all and Start-over all run with no exceptions.
**Notes / issues:** Streamlit button icons must be real emoji or `:material/...:` names; "↺" raised an exception, so Material icons are used.
